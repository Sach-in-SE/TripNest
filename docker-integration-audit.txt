2. DOCKER RUNTIME CONFIGURATION
================================================================================

- Backend Image: Built via multi-stage Temurin 17 JRE runtime.
- Frontend Image: Built via multi-stage Node 20 + Nginx 1.27 Alpine runtime.
- MySQL Image: Official `mysql:8.0`.
- Container Names: `tripnest-backend`, `tripnest-frontend`, `tripnest-mysql`.
- Port Mappings:
  * Host `80` -> Container `80` (Frontend Nginx).
  * Backend port `8080` is internal to `tripnest-network` (proxied by Nginx via `http://tripnest-backend:8080/`).
  * MySQL port `3306` is internal to `tripnest-network` (accessed by backend via `jdbc:mysql://tripnest-mysql:3306/tripnest_db`).
- Inter-Container Networking:
  * Shared bridge network `tripnest-network`. All DNS service names resolve (`tripnest-mysql`, `tripnest-backend`).
- Dependency Order & Healthchecks:
  * `mysql` initiates -> healthcheck ping validates ready state.
  * `backend` starts only after `mysql` is healthy -> healthcheck validates `/actuator/health`.
  * `frontend` starts only after `backend` is healthy.
- Healthcheck Note:
  * `frontend` healthcheck in compose uses `wget -q --spider http://127.0.0 || exit 1`. In certain BusyBox/Alpine environments, `http://127.0.0` is an incomplete IP notation that may fail if the resolver strictly requires `http://127.0.0.1` or `http://localhost`.
- Upload Volume Mapping:
  * Named volume `tripnest-uploads` is mounted at `/app/uploads` in `tripnest-backend`.
  * Backend environment variable `TRIPNEST_UPLOAD_DIR: /app/uploads` points directly to the mount path.

3. DATABASE CONFIGURATION & MIGRATION STRATEGY
================================================================================

3.1 Datasource Properties
- JDBC URL: `jdbc:mysql://tripnest-mysql:3306/tripnest_db?useSSL=false&allowPublicKeyRetrieval=true&serverTimezone=UTC`
- User: `tripnest_user`
- Password: Environment-injected `${SPRING_DATASOURCE_PASSWORD}`.
- Driver: `com.mysql.cj.jdbc.Driver`

3.2 Variable Mapping
- MySQL container creates database `tripnest_db` and user `tripnest_user` with password `${MYSQL_PASSWORD}`.
- Backend container connects using `SPRING_DATASOURCE_USERNAME=${SPRING_DATASOURCE_USERNAME:-tripnest_user}` and password `${SPRING_DATASOURCE_PASSWORD}`.
- Both align with the `.env` configuration.

3.3 JPA / Hibernate Settings
- `spring.jpa.hibernate.ddl-auto=update` (in default profile).
- `spring.jpa.defer-datasource-initialization=true` (ensures Hibernate schema is updated before `data.sql` executes).
- `spring.sql.init.mode=always` (forces `data.sql` destination seeding on startup).
- `spring.jpa.properties.hibernate.dialect=org.hibernate.dialect.MySQLDialect`.

3.4 Migration & Seeding Strategy
- Schema Initialization: Hibernate auto-generates/updates table structures on startup from JPA entities.
- Data Seeding (`src/main/resources/data.sql`):
  * Seeds 35+ Indian destinations across 7 categories into the `destinations` table with `ON DUPLICATE KEY UPDATE`.
- Code Initializers (`AdminInitializer.java`):
  * Implements `CommandLineRunner`.
  * Auto-provisions ERoles (`ROLE_TRAVELER`, `ROLE_GROUP_ADMIN`, `ROLE_ADMIN`) in the `roles` table if absent.
  * Auto-provisions or synchronizes the default System Administrator account (`admin@tripnest.com`) with `ROLE_ADMIN`.
- Destination Initializer (`DestinationDataSeeder.java`):
  * Secondary seeder ensuring 35 destinations exist in the database.
- Migration Frameworks:
  * Flyway: NOT present in `pom.xml`.
  * Liquibase: NOT present in `pom.xml`.
- Database Migration State:
  * The root directory contains a static database dump file `schema.sql` (created on 2026-08-17).
  * `docker-compose.yml` does NOT mount `schema.sql` into `/docker-entrypoint-initdb.d/`.
  * Therefore, a newly spun up Docker MySQL container starts with an empty database, which is subsequently initialized solely via Hibernate `ddl-auto=update`, `data.sql` (destinations), and `AdminInitializer` (admin user + roles). No historical user data is migrated automatically.

- Base URL: `import.meta.env.VITE_API_URL || 'http://localhost:8080/api'`

7. DOCUMENT STORAGE AUDIT (DETAILED TRACE)
================================================================================

Flow Trace:
Documents.jsx
  -> Axios `api.post('/documents/upload', formData)` / `api.get('/documents/download/...')`
  -> Frontend Nginx `location /api/`
  -> `proxy_pass http://tripnest-backend:8080/api/`
  -> `DocumentController`
  -> `DocumentService`
  -> `DelegatingStorageService` -> `LocalStorageService`
  -> Filesystem Path: `/app/uploads/{storedFileName}`
  -> Docker Named Volume: `tripnest-uploads`

Operation Breakdown:
1. Upload (`POST /api/documents/upload`):
   - Frontend selects file, validates MIME and 10MB limit.
   - Nginx receives request (`client_max_body_size 15M;`) and proxies to backend.
   - `DocumentController` extracts user authentication.
   - `DocumentService`:
     * `DocumentFileValidator.validateFile` verifies extension and magic bytes (PDF, JPEG, PNG, WEBP, DOCX, TXT).
     * Validates trip ownership or share edit access.
     * Generates `storedFileName = UUID.randomUUID() + extension`.
     * `storageService.storeFile(file, storedFileName)` writes file bytes to `/app/uploads/{storedFileName}`.
     * Creates `TravelDocument` record with `fileUrl = "/api/documents/download/" + storedFileName`.
     * Returns `DocumentResponse`.
2. List (`GET /api/documents/trip/{tripId}`):
   - Validates user access to trip.
   - Retrieves documents by `tripId` and returns metadata list.
3. Download / View (`GET /api/documents/download/{fileName}`):
   - Frontend receives `fileUrl: "/api/documents/download/UUID.ext"`.
   - Frontend extracts `/documents/download/UUID.ext` and issues `api.get(endpoint, { responseType: "blob" })`.
   - `DocumentController.downloadFile` requires authenticated user (`getCurrentUser()`).
   - `DocumentService.getDocumentResource` validates against path traversal (`..`, `/`, `\`), confirms trip access in database, loads resource from `/app/uploads/{fileName}`, and returns `ResponseEntity<Resource>`.
   - Frontend converts blob into `URL.createObjectURL(blob)` for viewing in new tab or downloading.
4. Delete (`DELETE /api/documents/{id}`):
   - Validates uploader or trip owner permissions.
   - Removes file from `/app/uploads/{storedFileName}` via `storageService.deleteFile`.
   - Deletes entity from database.

8. TRAVEL MEMORY STORAGE AUDIT (DETAILED TRACE)
================================================================================

Flow Trace:
Memories.jsx
  -> Axios `api.post('/memories', formData)` / `api.get('/memories/photo/...')`
  -> Frontend Nginx `location /api/`
  -> `proxy_pass http://tripnest-backend:8080/api/`
  -> `TravelMemoryController`
  -> `TravelMemoryService`
  -> `DelegatingStorageService` -> `LocalStorageService`
  -> Filesystem Path: `/app/uploads/memory_{UUID}.{ext}`
  -> Docker Named Volume: `tripnest-uploads`
  -> Database Metadata: `travel_memories`

Operation Breakdown:
1. Create Memory (`POST /api/memories`):
   - Multipart payload contains image file, title, optional caption, location, tripId, destinationId, visibility.
   - `TravelMemoryService`:
     * Validates image MIME and magic bytes.
     * Validates user and optional trip/destination links.
     * Generates `storedFileName = "memory_" + UUID.randomUUID() + extension`.
     * Writes image to `/app/uploads/{storedFileName}`.
     * Saves `TravelMemory` entity with `storedFileName`, `imageUrl = "/api/memories/photo/" + storedFileName`, `visibility = PRIVATE | PUBLIC`.
2. List Memories (`GET /api/memories` & `GET /api/memories/public`):
   - `GET /api/memories`: Returns memories belonging to current user ordered by `createdAt DESC`.
   - `GET /api/memories/public`: Returns all memories with `visibility = 'PUBLIC'`.
3. Photo Serving & Cache (`GET /api/memories/photo/{fileName}`):
   - Nginx and Spring Security permit public requests to `/api/memories/photo/**`.
   - `TravelMemoryController.getPhoto` calls `travelMemoryService.getMemoryPhotoResource`.
   - If memory is `PRIVATE`, verifies current authenticated user is the memory owner.
   - Returns image `Resource` with Cache-Control headers.
   - Frontend `fetchMemoryPhotoBlobUrl` fetches via Axios with JWT, receives Blob, and creates Object URL cached in `memoryBlobCache` Map.
4. Update (`PUT /api/memories/{id}`):
   - Updates title, caption, location, visibility, trip, destination.
5. Delete (`DELETE /api/memories/{id}`):
   - Verifies owner, deletes image file from `/app/uploads/{storedFileName}`, deletes entity, and invalidates frontend blob cache.

9. BUDGET AUDIT (DETAILED TRACE)
================================================================================

Flow Trace:
Budget.jsx
  -> Axios `api.get('/budget/trip/{tripId}')` / `api.post('/budget', ...)`
  -> Nginx Proxy
  -> `BudgetController`
  -> `BudgetService`
  -> `BudgetRepository` (`budgets`) & `ExpenseRepository` (`expenses`)

Trace Analysis:
1. Fetching Budget (`GET /api/budget/trip/{tripId}`):
   - `BudgetService.getBudgetByTripId`:
     * Verifies trip access.
     * Searches `budgetRepository.findByTripId(tripId)`.
     * If no budget has been set yet for the trip, throws `RuntimeException("Budget not found")`.
     * This causes a 500 error response from the backend (or 400/500 depending on handler).
     * `Budget.jsx` handles this via try/catch and sets `setBudget(null)`, allowing the UI to display the "Set Budget" option.
     * If budget exists, recalculates `spentAmount` from `expenseRepository.getTotalExpenseByTripId(tripId)` and updates `remainingAmount = totalAmount - spentAmount`.
2. Creating / Updating Budget (`POST /api/budget`):
   - `BudgetService.createOrUpdateBudget`:
     * Verifies owner or shared trip EDIT permission.
     * Updates or creates new `Budget` entity.
     * Calculates `spentAmount` and `remainingAmount`.
     * Saves entity via `budgetRepository.save(budget)`.
     * Entity Lifecycle Quirk: In `Budget.java`, `@PrePersist` sets `remainingAmount = totalAmount;`. When creating a brand new budget on a trip that already contains expenses, the `@PrePersist` hook resets `remainingAmount` to `totalAmount` on initial insert. Subsequent reads recalculate it properly.
3. Expense Integration:
   - `POST /api/expenses` and `PUT /api/expenses/{id}`:
     * Saves expense and triggers `checkBudgetAlerts(trip)`.
     * Sends `BUDGET_ALERT` notification if total spent reaches 80% or 100% of budget.
4. UI Behavior for Fresh Users:
   - When a newly registered user logs in, `trips` array is empty `[]`.
   - In `Budget.jsx`, `selectedTrip` initializes to `null`.
   - Because `{selectedTrip && ...}` wraps the entire budget card, statistics, and forms, the page renders only the header with an empty section below, lacking an empty state prompt guiding the user to create a trip.

10. AUTH & USER DATA AUDIT (DOCKER FRESH DB ANALYSIS)
================================================================================

10.1 Why Old Users Cannot Log In Against Fresh Docker DB
- Cause: The Docker Compose MySQL instance uses a fresh local volume (`tripnest-mysql-data`).
- The database is completely empty upon first launch.
- Historical user accounts existed solely in the previous standalone/local MySQL instance and are not contained in the Docker volume.
- No automatic user import, seed file, or database dump restore (`schema.sql`) is mounted or executed during container initialization.
- Consequently, attempting to log in with credentials from the old database fails with `401 Unauthorized` / `BadCredentialsException` because the user record does not exist in the new database.
- This is 100% expected behavior for a freshly initialized Docker container volume.

10.2 Role & Admin Provisioning
- Roles Seeding: Handled automatically on startup by `AdminInitializer.java`.
  * Provisions `ROLE_TRAVELER`, `ROLE_GROUP_ADMIN`, `ROLE_ADMIN` if missing.
- Administrator Seeding:
  * Seeds default administrator (`admin@tripnest.com` / `admin`) with `ADMIN_PASSWORD` from `.env`.
  * Synchronizes password hash and ensures `ROLE_ADMIN` and `enabled=true`.
- Password Compatibility:
  * Uses standard BCrypt hashing via `BCryptPasswordEncoder`. Any user created via `/api/auth/signup` or seeded by `AdminInitializer` functions seamlessly.
- JWT User ID Mapping:
  * JWT tokens encode the `username` as the subject claim.
  * In incoming requests, `AuthTokenFilter` extracts username, loads `UserDetailsImpl` via `UserDetailsServiceImpl`, and injects current user ID into `SecurityContextHolder`. User ID matches the current database ID.
